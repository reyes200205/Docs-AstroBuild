Esta guía establece los **estándares de calidad, arquitectura y flujo de trabajo** para el equipo de desarrollo de la plataforma Master Drilling. El objetivo principal es garantizar que el código del backend (`laravel-api-kit`) y del frontend (`nuxt-app-kit`) sea consistente, mantenible, seguro y escalable a largo plazo.

<Aside type="tip" title="Principio fundamental">
El código se escribe una vez, pero se lee, refactoriza y mantiene docenas de veces. Cada contribución debe priorizar la claridad, el tipado fuerte y la separación de responsabilidades sobre atajos temporales.
</Aside>

## Qué encontrarás en esta sección

### 1. Gestión de dependencias
- **Frontend (Node / pnpm)**: Uso obligatorio de `pnpm`, control estricto del archivo `pnpm-lock.yaml`, auditoría periódica de vulnerabilidades con `pnpm audit` y políticas para evitar librerías redundantes.
- **Backend (PHP / Composer)**: Manejo de versiones exactas, distinción clara entre `require` y `require-dev`, y automatización de actualizaciones seguras.

### 2. Estructura y arquitectura del proyecto
- **Separación de capas en Laravel**: Controladores delgados (Lean Controllers), Servicios de Dominio (Domain Services), Form Requests para validación y Recursos (API Resources / DTOs) para respuestas estandarizadas.
- **Arquitectura en Nuxt 4**: Componentes atómicos con Nuxt UI, Composables para lógica reutilizable, manejo centralizado de estado y tipado estricto en el consumo de endpoints.

### 3. Flujo de trabajo y Git
- **Estrategia de ramas**: Modelo Git Flow adaptado (`main`, `develop`, ramas de características `feature/*` y correcciones `fix/*`).
- **Commits semánticos**: Formato convencional (`feat:`, `fix:`, `refactor:`, `docs:`, `chore:`) para trazabilidad clara en el historial del repositorio.
- **Revisiones de código (Pull Requests)**: Criterios de aceptación antes de fusionar código a las ramas principales.

El detalle está en [Flujo de Git](/development/git-workflow/), [Pull requests](/development/pull-requests/) y [Calidad del código](/development/code-quality/).

### 4. Seguridad y manejo de variables de entorno
- Ningún secreto, credencial de API, llave S3 o token de base de datos debe ser versionado en Git.
- Uso riguroso de archivos `.env.example` sincronizados con cualquier nueva variable requerida por el sistema.

## Convenciones de código rápidas

| Aspecto | Backend (`laravel-api-kit`) | Frontend (`nuxt-app-kit`) |
|---|---|---|
| **Lenguaje** | PHP 8.4 | TypeScript / Vue 3 |
| **Estilo / Linter** | Laravel Pint (preset Laravel), Rector y PHPStan | ESLint (`@nuxt/eslint`) y `nuxt typecheck` |
| **Archivos / Clases** | PascalCase (`UserController.php`) | PascalCase en componentes (`UserCard.vue`), camelCase en composables (`useAuth.ts`) |
| **Métodos y funciones** | camelCase (`findActiveUsers()`) | camelCase (`fetchUserProfile()`) |
| **Tablas y columnas DB** | snake_case plural (`users`, `created_at`) | — |
| **Rutas API** | kebab-case (`/api/v1/auth/reset-password`) | — |

<Aside type="caution" title="Regla de oro de documentación">
Cualquier cambio que modifique una convención de arquitectura, agregue una variable de entorno obligatoria o cambie un flujo de Git debe quedar reflejado de inmediato en esta documentación.
</Aside>
